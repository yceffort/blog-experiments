# E10. 여러 브라우저가 한 시리즈에 쓰면 delta_to_cumulative 가 얼마나 버리는가

브라우저의 metric 은 라벨 조합이 같으면 모두 한 시리즈다. resource 속성도 `service.name` 뿐이라 브라우저마다 다르지 않다. 그런데 `delta_to_cumulative` 는 시리즈 하나를 한 프로세스가 차례로 보낸다고 가정한다. [E9](../e9-client-clock) 는 시계가 어긋난 브라우저 3개로 그 가정이 깨지는 것을 봤고, 여기서는 트래픽이 많을 때 얼마나 버리는지 잰다. 브라우저 대신 OTLP 요청을 직접 만든다.

## 버리는 규칙

`internal/delta/delta.go` 의 `Aggregate`(v0.163.0, v0.162.0 과 같다)는 시리즈의 첫 값으로 시작 시각을 정하고, 그 뒤의 값을 두 가지로 버린다.

- 시작 시각이 시리즈의 시작 시각보다 이르면 `ErrOlderStart`
- 시각이 지금까지 받은 가장 늦은 시각 이하면 `ErrOutOfOrder`

버린 값도 만료 타이머는 갱신한다. `processor.go` 의 `ConsumeMetrics` 는 집계하기 전에 `p.stale.Store(id, now)` 를 부르므로, 값이 계속 들어오는 동안은 모두 버려지더라도 시리즈가 만료되지 않는다(`max_stale` 기본 5분).

## 실행

```bash
docker compose up -d            # cwv-otel-grafana 에서
cd experiments
node e10-concurrent-writers/run.mjs jitter a       # 약 4분
node e10-concurrent-writers/run.mjs one-fast a     # 약 3분
node e10-concurrent-writers/run.mjs far-future a   # 약 8분
node e10-concurrent-writers/run.mjs skew2014 a     # 약 5분
node e10-concurrent-writers/predict.mjs a b        # 같은 입력에 규칙만 적용한 계산(docker 불필요)
```

- 페이지 로드는 Poisson 과정으로 일어나고, 값마다 LCP 1건짜리 delta 히스토그램을 보낸다. 시작 시각은 시각보다 0~10초 앞(브라우저의 10초 export 주기)이다.
- 값은 50~550ms 사이의 균등한 네트워크 지연 뒤에 도착한다. **이 분포는 실측이 아니라 가정이다.**
- 입력은 명령의 마지막 인자(seed)로 만든다. 같은 seed 면 같은 입력이고, `predict.mjs` 도 같은 입력을 만든다. 보내는 시각과 시작 시각은 두 스크립트 모두 `scenarios.mjs` 의 `stamps` 로 정수 ms 로 맞춘다.
- run 라벨은 seed 뒤에 실행 시각을 붙여 실행마다 새로 만든다. lab collector 는 계속 떠 있어서, 같은 라벨을 5분 안에 다시 쓰면 앞 실행의 누적 상태를 이어받는다([E8](../e8-sparse-counts) 의 첫 실행 이상값과 같은 원인).
- collector-contrib 0.163.1, Mimir 3.2.2. 세 경로에 같은 값을 동시에 보낸다(경로 구성은 E9 와 같고 collector 설정도 E9 의 것을 쓰되 Mimir 주소만 `e10-mimir` 로 바꾼다).

| 경로 | 처리 |
|---|---|
| lab | lab 의 collector(`delta_to_cumulative`, remote write). 남은 건수는 Mimir 누적값의 최댓값 |
| client_time | delta 를 그대로 Mimir OTLP 엔드포인트로, 시각은 브라우저 것 그대로. 남은 건수는 `sum_over_time` |
| receive_time | client_time 과 같고 시각을 collector 가 받은 시각으로 바꾼다(블로그 운영 구성과 같다) |

| 시나리오 | 내용 |
|---|---|
| jitter | 시계는 모두 맞다. 시리즈 하나에 초당 1, 10, 50건을 각 60초 |
| one-fast | 초당 2건 120초, 20초에 시계가 60초 빠른 브라우저 하나 |
| far-future | 초당 1건 420초, 10초에 시계가 2시간 빠른 브라우저 하나 |
| skew2014 | 시계 편차를 2014년 공개 측정 분포에서 뽑는다. 초당 1, 10건을 각 120초 |

skew2014 의 분포는 2014년 하루 3억 페이지 로드에서 브라우저의 `Date()` 와 서버 시각을 비교한 자료다([CA/B Forum 메일링 리스트, 2014-11-03](https://lists.cabforum.org/pipermail/public/2014-November/020810.html)). 5분 단위로 묶은 절댓값의 백분위가 90% 5분 미만, 99% 115분 미만, 99.9% 1530분 미만, 99.99% 76320분 미만이고, 앞선 쪽이 약 57% 다. 공개된 것은 이 백분위 경계와 부호 비율뿐이라 나머지는 가정으로 채웠다. 5분 미만 구간은 분포가 공개되지 않아 편차를 0 으로 두었고, 나머지 구간 안에서는 절댓값을 균등하게 뽑고, 상위 0.01% 는 76320분으로 고정하고, 부호는 크기와 무관하게 57% 확률로 앞서게 했다. 그래서 이 시나리오는 2014년 공개 백분위에 맞춘 가정 모델이지 관측 분포가 아니다. 편차 0 이 손실을 가장 줄인다는 보장도 없어서 결과를 손실의 하한으로 읽으면 안 된다. 늦게 수집된 값도 시계가 조금 앞서 직전 값보다 늦은 시각이 되면 살아남기 때문이다. 자료가 오래됐고 미국, 캐나다, EU 사이트에 치우쳐 있어 지금의 모바일 웹뷰와는 다를 수 있다.

### 규칙만으로 계산한 값과 거의 같다

`predict.mjs` 로 같은 입력에 두 규칙만 적용한 값과, collector 자체 메트릭 `otelcol_deltatocumulative_datapoints` 로 센 실측(받아들인 건수 / `ErrOlderStart` / `ErrOutOfOrder`)이다.

| jitter-1-b | 60 / 0 / 6 | 60 / 0 / 6 |

14개 중 12개가 같고 jitter-10-a 와 jitter-50-a 만 1건씩 다르다. 처음 계산은 시각을 소수 ms 그대로 비교해서 넷이 달랐다. 송신기는 정수 ms 로 보내므로 같은 ms 로 반올림된 값은 실제로 `ErrOutOfOrder` 가 되는데, 계산은 그 값을 받아들였다. 정수 ms 로 맞추자 jitter-10-b 와 jitter-50-b 는 같아졌다. 고친 runner 로 seed `a` 의 jitter 를 다시 돌리자 jitter-10-a 는 계산과 같았고(340 / 4 / 259), jitter-50-a 는 751 / 19 / 2286 으로 이번에는 반대쪽으로 1건 달랐다. 같은 입력에서도 실행마다 1건씩 흔들리므로, 남은 차이는 계산이 도착 순서를 송신 예정 시각으로 정하는 것과 실제 송신, 처리 순서의 차이로 본다(실제 순서는 기록하지 않았다). 손실은 두 규칙으로 거의 전부 설명된다.

### 시나리오별

- **jitter:** 시계가 모두 맞아도 잃는다. 늦게 수집된 값이 지연이 짧아 먼저 도착하면 시리즈의 시각이 올라가고, 그보다 일찍 수집됐지만 늦게 도착한 값이 `ErrOutOfOrder` 가 된다. 그래서 잃는 비율은 시리즈 하나의 초당 건수와 지연의 폭에 따라 커진다.
- **one-fast:** 60초 빠른 값 하나가 들어오면 시리즈의 시각이 60초 앞으로 가고, 그 뒤 60초 동안 들어온 값은 모두 버려진다. lab 의 누적 시리즈에서 표본 사이 가장 긴 공백이 60.2초, 60.1초였다.
- **far-future:** 2시간 빠른 값 하나 뒤로 7분 동안 1건도 남지 않았다(처음 10초의 5건, 6건만 남음). 7분은 `max_stale` 5분과 1분 검사 주기를 넘지만, 버린 값도 만료 타이머를 갱신하므로 시리즈는 만료되지 않았다. 그 2시간 빠른 값의 누적 표본은 Mimir 가 `too_far_in_future` 로 거부했다(`-validation.create-grace-period` 기본 10분, 13개 시리즈 = 버킷 11개, count, sum). 값이 계속 들어오는 한 이 시리즈는 2시간 동안 멈춘다.
- **skew2014:** 처음으로 앞선 시계가 들어온 뒤로는 그보다 더 앞선 시계만 통과한다. 계산으로 본 초당 10건의 생존 값은 편차 0 하나와 50.7분, 60.6분, 75.9분, 86.0분, 1166분, 23285분 앞선 값(a)이었고, 앞선 값은 Mimir 의 10분 유예를 넘어 다시 거부되어 Mimir 에는 1건만 남았다. 초당 1건은 앞선 시계가 언제, 얼마나 앞서 들어오느냐에 따라 크게 달라진다(같은 분포에서 seed `c` 의 입력은 121건 중 63건이 남는다고 계산된다).
- **client_time:** Mimir 도 시리즈마다 시각이 늘어나야 받으므로(`-ingester.out-of-order-time-window` 기본 0) jitter 는 lab 과 거의 같다. 다만 앞선 시계의 값이 10분 유예를 넘으면 Mimir 가 그 값만 거부하고 시리즈의 시각은 올라가지 않으므로, far-future 에서는 lab 보다 훨씬 적게 잃는다.
- **receive_time:** 시계와 도착 순서의 영향을 받지 않는다. 대신 초당 10건부터 같은 밀리초에 받은 값끼리 같은 시각의 표본이 되어 Mimir 가 `sample_duplicate_timestamp` 로 버린다(초당 50건에서 6.7~7.5%). 같은 밀리초에 다른 값이 도착할 확률은 대략 초당 건수 × 1ms 이므로 초당 50건이면 5% 안팎을 예상했는데, 송신기의 타이머가 같은 밀리초에 몰아 보낸 영향이 더해졌을 수 있다(확인하지 않았다).

같은 입력을 gateway 가 모아 하나의 writer 로 내보내면 잃지 않는다([E11](../e11-server-aggregation)).
